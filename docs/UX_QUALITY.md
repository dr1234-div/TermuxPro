# TermuxPro 产品体验质量基线

TermuxPro 的核心价值不是堆叠终端功能，而是让用户在手机上以更少判断、更少操作和更低风险完成远程
开发。UI/UX 与 SSH、tmux、Claude Code、Codex 的功能正确性同等重要，不能作为发布前的美化环节。

## 体验原则

1. **大道至简**：当前任务只突出一个主操作；次要能力渐进展示，高危操作不长期占据主视觉。
2. **状态诚实**：只展示已验证事实，清楚区分未连接、连接中、待确认、失败、已连接和会话已进入。
3. **安全且可预期**：默认不进入未知 tmux 或共享 Claude 历史会话；任何恢复动作都让用户先看到目标。
4. **随时可恢复**：网络中断、切后台、误触返回、软键盘遮挡后，用户仍知道当前状态和下一步。
5. **移动优先**：为单手、软键盘、窄屏、中文、大字体和碎片时间设计，不照搬桌面终端的信息密度。
6. **克制一致**：相同状态使用相同文案、颜色和反馈；避免重复入口、重复解释和没有下一步的提示。

## 必须持续走查的核心旅程

每轮体验审计至少选择一条主旅程，从用户视角实际操作并保存当轮证据，不凭代码或旧截图推断：

1. 首次创建 SSH 工作区，识别主机指纹并成功连接。
2. 从最近工作区快速重连，处理弱网、中断、认证失败和远端环境缺失。
3. 仅进入 SSH Shell，不自动进入任何 tmux 会话。
4. 查看 tmux 全量会话，识别归属和风险，显式进入指定会话。
5. 新建 Claude Code/Codex 会话，或从历史列表显式选择并恢复。
6. 在软键盘下输入命令、切换终端辅助键、返回首页并继续原任务。
7. 查看远程文件、Git 修改、项目任务和 Web 隧道，再安全返回终端。

## 主动体验闭环

产品负责人不得等待用户提交截图后才发现问题。每轮按以下顺序执行：

1. **体验**：使用当前候选 APK 按主旅程操作；覆盖简体中文、深色主题、360dp、默认与 200% 字体。
2. **观察**：记录完成任务所需点击数、必须理解的选择数、滚动屏数、等待点、误触风险和失败恢复路径。
3. **登记**：将问题写入 `docs/PRODUCT_BACKLOG.md`，包含当轮证据、影响旅程、严重级别和可验证验收标准。
4. **设计**：先删除不必要信息和步骤，再考虑新增控件；涉及结构变化时先形成截图或原型目标。
5. **实现**：按纵向切片完成 UI、交互、文案、异常状态、测试和文档，不只修单个截图里的控件。
6. **回归**：重新走完整主旅程并对比改前/改后指标；未改善或引入新困惑则退回继续迭代。

## 持续发现与自我纠偏

现有需求、页面、架构、Backlog、测试和本文都只是当前假设，不是不可改变的结论。产品负责人每轮除处理
已知任务外，必须主动完成一次“反向评审”：</n+
- 这个能力是否解决高频真实问题，还是因为已经开发了就被保留？
- 能否删除、合并或自动化一个步骤，而不是继续增加入口和选项？
- 默认值是否适合个人账号、共享账号、多用户服务器、无 tmux 和弱网等不同场景？
- 成功状态是否由事实证明，失败后是否能无损恢复，用户是否知道接下来该做什么？
- 当前实现是否给后续维护、上游同步、性能、安全或发布制造了不成比例的成本？
- 自动化是否只验证了“能运行”，却遗漏了用户完成任务的真实路径？

发现更优方案时可以调整现有规则、设计和技术实现，但必须说明旧假设、证据、预期收益、风险与回滚方式，
并通过小范围可回归切片验证。不得因为“文档已经写好”或“功能已经完成”拒绝改进。

## 产品健康巡检面

每轮从下列维度轮换主动发现问题，不允许长期只迭代功能数量：

| 维度 | 主动检查问题 |
|---|---|
| 用户价值 | 是否服务手机 SSH + AI CLI 高频任务，是否存在低价值功能或缺失的关键旅程 |
| 易用与体验 | 是否简单、清楚、少步骤、可单手操作，并在中文、大字体、软键盘下仍然舒服 |
| 可靠与恢复 | 弱网、断连、后台、进程死亡、远端缺依赖后能否诚实提示并恢复 |
| 隐私与安全 | 主机指纹、密钥、共享账号、tmux/AI 历史会话是否避免越权和误入 |
| 性能与资源 | 启动、滚动、终端输入、内存、电量、网络流量和远端命令是否克制 |
| 可维护性 | 与上游 Termux 的差异是否可控，重复逻辑、债务和测试盲区是否持续减少 |
| 交付质量 | 构建、签名、升级、回滚、Release 和真机证据是否可复现且没有虚假通过 |

巡检输入包括真实使用反馈、当前版本亲自走查、GitHub Issue/CI/崩溃、代码与依赖风险、测试缺口、Android
平台变化，以及同类产品中已经被验证的交互范式。竞品只用于发现问题和验证范式，不照搬其产品结构。

## 缺陷分级

- **P0**：无法完成核心旅程、误入他人/共享会话、状态误导、凭据风险、文字不可读或关键操作被遮挡。
- **P1**：可完成但步骤明显冗余、信息层级混乱、恢复困难、重复入口、滚动负担过大或跨页面不一致。
- **P2**：不阻断任务的视觉精度、动效、细节一致性和锦上添花能力。

视觉瑕疵不能因为“不影响功能”而自动降级；若它让用户看不清、找不到或不敢操作，应按 P0/P1 处理。

## 体验门禁

一个涉及用户界面的功能只有同时满足以下条件才算完成：

- 主操作在当前状态下明确，页面没有同等强调的竞争操作。
- 用户不需要理解实现术语即可预测按钮结果；错误提示包含安全、可执行的下一步。
- 360dp、简体中文、深色主题、默认与 200% 字体下无裁切、重叠、黑字或不可达控件。
- 软键盘弹出、系统返回、应用切后台及网络重连不会丢失未保存输入或制造虚假成功状态。
- 高危操作有明确对象和确认，安全默认值不会进入未知 tmux/Claude 共享历史会话。
- 自动化截图只证明可见布局；触控、输入法、TalkBack、弱网与真实 SSH 仍按适用门禁实测。

## 体验度量

体验指标用于发现摩擦，不用于为了数字牺牲安全：

- 从首页到 SSH Shell、指定 tmux、Claude/Codex 新会话的点击数和滚动屏数。
- 首屏主操作数量、重复入口数量、需要用户自行推断的状态数量。
- 失败后回到可操作状态所需步骤，以及未保存内容是否保留。
- 默认字体与 200% 字体的核心操作可见性、触控目标和页面长度变化。
- 同一任务改版前后的完成路径对比和回归缺陷数。

## 证据边界

模拟器截图适合检查层级、布局、文案、主题和大字体重排，不能独立证明真实输入法、触控手感、网络切换、
后台恢复、TalkBack 或厂商 ROM 行为。无法在共享服务器安全运行模拟器时使用 GitHub Runner；需要真机的
结论必须保留为待验收，不得写成通过。
