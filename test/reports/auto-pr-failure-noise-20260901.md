# 自动 PR 失败邮件噪声排查记录（2026-09-01）

## 背景

用户反馈 GitHub 邮件中持续收到 PR 和 CLI/CI 相关失败提示，且感知不到成功提示。

## 当前事实

近 30 次 GitHub Actions 中，稳定发布、master CI、dev CI、多数研发分支 CI、模拟器 UI 和自动 PR
均存在成功记录；不是流水线整体不可用。

用户收到失败邮件的主要原因是：研发分支中间提交失败后，后续强推修复会重新触发成功运行，但 GitHub
不会撤回已发送的旧失败邮件。

## 确认的问题

`自动创建研发 PR` workflow 以前会等待预合并 CI 和模拟器 UI。如果其中任一失败，自动 PR workflow
也以 failure 结束。这样同一个代码问题会至少产生两类失败：

1. 真正的门禁失败，例如 `TermuxPro CI`。
2. 派生的自动 PR 失败，即“因为 CI 没过所以没有合并”。

第二类失败不提供新的诊断价值，会增加邮件噪声。

## 修复

预合并 `完整 CI` 或 `模拟器 UI` 未通过时，自动 PR workflow 现在会：

1. 保留 PR，等待后续提交修复。
2. 输出明确日志。
3. 以成功状态结束，避免与真实 CI 失败重复发送失败邮件。

以下失败仍应保留为 failure：

- 自动 PR 创建失败、权限失败或 GitHub API 调用失败。
- PR 已合并到 `dev` 后，`dev` 收尾 CI 失败。
- 候选 Release 创建、签名、验收或发布失败。

这些属于真实链路风险，需要维护者处理。

## 验收

- `./test/workflow-trigger-policy-test.sh` 增加静态规则，防止预合并门禁失败再次直接导致自动 PR failure。
- 后续推送本分支后观察：若 CI 失败，应只由 CI 自身失败；自动 PR 不再重复失败。
